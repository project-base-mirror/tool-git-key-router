# GitKeyRouter v0.4.27 开发记录

## 问题与根因

用户在 v0.4.25 的更新流程遇到“无法检查更新。The process cannot access the file because it is being used by another process.”。v0.4.25、v0.4.26 与本轮基线 main `16962e0` 的 UpdateDownloadService 相同。

元数据检查只读取网络响应，不写本地文件。发现新版本后的下载路径为 `<AppData>/updates/v<版本>/GitKeyRouter-v<版本>-win-x64-*.msi.partial`。旧代码以 FileShare.None 打开该文件，在 `await using var` 作用域结束前调用 File.Move；在 Windows 上，该文件仍被应用自己的句柄独占，重命名会触发 sharing violation。MainForm 将检查、下载及启动都放在同一个 catch 内，导致下载失败也显示“无法检查更新”。这是代码和隔离测试确认的缺陷；未访问用户电脑上的日志或配置。

## 修复

- 将写入、flush 和 SHA-256 校验限定在文件流作用域内，等待 DisposeAsync 完成后才重命名；取消或失败仍清理本次临时文件。
- 每次下载使用独立的随机临时路径，只清理自己创建的文件；不删除旧版遗留或其他请求持有的 `.partial`。
- 用异步 SemaphoreSlim 串行化进程内各下载服务实例的缓存校验和发布。等待支持取消，释放位于 finally；GUI 的单实例锁与更新检查防重入保护保持有效。
- 已校验缓存可重复使用；校验失败不覆盖原有文件，重试不被上次失败阻塞。
- 界面分别报告发布信息检查失败和发现版本后的更新失败，中英文 README 提供旧版本的手动覆盖升级方法。

## Gitee 服务类型补充

新增枚举 Gitee，固定旧枚举的数值为 GitHub=0、GitLab=1、Gitea=2、Generic=3，Gitee 追加为 4。下拉框、模板、CLI JSON 均直接显示/接受 Gitee。GiteeProviderAdapter 复用 StandardGitProviderAdapter，与旧 Generic 路由、SSH 和认证成功识别保持一致，不套用 Gitea 特例。

配置加载只将 Generic 且主机精确等于 gitee.com（忽略大小写、两端空白）的记录识别为 Gitee；ID、默认身份、路由和 Profile 引用保持不变，不在只读加载时写文件。字符串及数值形式的新旧枚举均覆盖 round-trip，其他主机和显式 Gitea 类型不改写。新增 UI 测试覆盖模板选中 Gitee 和手动将已有 Generic 改为 Gitee。

## 验证与发布

使用临时目录、模拟 HTTP 响应和不可执行的模拟安装包，不访问真实凭据、Git/SSH 配置，也不启动安装器。测试覆盖两种 MSI 的首次下载及重复缓存命中、九个并发调用、取消等待者、取消进行中的下载后重试、损坏下载与缓存恢复、不删除被锁定的旧临时文件，以及 16 个并发和 3 次重复元数据检查。

新增回归测试在旧程序集上复现并发临时文件冲突；Windows 上的首次下载测试直接覆盖原始独占句柄重命名路径，并在返回后以 FileShare.None 重新打开目标文件确认句柄已释放。

- 本地 locked restore、Windows 目标 Release 构建（0 警告/错误）及格式检查通过。隔离更新测试 8/8、Gitee/服务管理 31/31、CLI 64/64 通过。
